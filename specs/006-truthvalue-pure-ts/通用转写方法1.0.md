# 通用转写方法 1.0

目的：把 Java 风格模块转写为 TypeScript 的同时，保留核心语义、降低耦合并可验证。

## 核心原则

- 测试先行：先锁定行为，再动实现。
- 依赖降维：先切断高层依赖，再下沉实体。
- 语义优先：保留计算与约束，移除仪式化 Java 语义。
- 小步回归：每一步都能跑最小测试。

## 通用流程（8 步）

1) 依赖剥离
   - 在动手前先盘点目标文件的“公开面”：常量、类型、API、索引结构（必须输出清单）。
   - 清单必须来源于实际扫描结果（rg/查看源码），避免“凭印象遗漏”。
   - 记录所有静态初始化与运行期副作用，作为回归测试重点。
   - 低层模块不依赖高层模块：值对象/实体层不得直接依赖语言/控制/推理层。
   - 识别“表面依赖”与“结构性依赖”：仅用于展示/格式化的依赖应上移。
   - 高层需求通过适配器/格式化层实现：把转换/展示逻辑移到同层适配器或更高层。
   - 必须保留依赖时，显式在调用端引入，避免在基础类型中隐藏依赖。
   - 落地方式：在原文件同目录新增后缀文件承载迁移逻辑，例如：
     - `TruthValue.ts` → `TruthValueTerm.ts`（或 `TruthValueAdapter.ts`）
     - 规则：文件名保留原名 + 明确后缀，方便检索与溯源

2) 测试锁定
   - 先写测试覆盖核心行为与边界条件。
   - 为静态初始化/副作用写回归测试（如 IN/OUT/ERR）。
   - 增加索引结构/映射一致性测试（size/唯一性/互查）。
   - 若存在名称规则（如 opener/closer），必须测试规则一致性。
   - 测试应独立于 Java 语义（例如 StringBuilder/Serializable）。

3) 纯 TS 设计草案
   - 明确要保留的语义与边界条件，删除 Java 仪式性结构。
   - Java 语义 → TypeScript 替代清单：
     - `Serializable` → 移除；需要持久化时改为显式序列化函数
     - `Cloneable/clone()` → 显式工厂或 `copy()` 方法
     - `hashCode/equals` → 删除或改为 `toKey()` 字符串键
     - `java.lang.Math` → 原生 `Math`
     - `StringBuilder`/`CharSequence` → 字符串拼接或数组 join
     - `int/float/double` → `number` + 运行时校验
     - 构造重载 → 具名工厂函数
     - Java 异常类型 → `Error` 或自定义 Error
     - Java `enum` → TS `enum`；若带属性/方法则用 `const` 对象 + `as const`
   - 定义 TypeScript 风格 API：公共字段 + 最少 getter/setter（只在有逻辑时保留）。

4) 重写实现
   - 直接替换为纯 TS 类型与逻辑。
   - 把“计算/约束”留在 setter 或显式方法中。

5) 构造策略统一
   - 只保留“字段一一对应”的构造函数。
   - 其余构造逻辑改为具名工厂方法。

6) 调用点改造
   - 批量替换 `new` 用法与旧式 `get/set` 调用。
   - 保持调用点语义等价。
   - 改造前先生成调用点清单（必须输出清单），避免遗漏隐性依赖。
   - 替换规则必须建立在“实际存在的 API”之上，先确认后替换，避免虚构 API。

7) 运行期阻塞修复
   - 若测试因运行期依赖失败，先移除/内联常量或最小 stub。
   - 确保测试能跑通，再回头调整依赖结构。

8) 回归验证
   - 运行最小测试集。
   - 通过后更新 spec 状态与报告记录。

## 可复用清单

- 低层类对高层依赖的剥离点
- 行为测试覆盖范围
- 具名工厂函数命名规范
- 运行期依赖阻断策略

## 适用范围

- 值对象、实体对象、规则函数、配置类
- 依赖链较深、Java 语义负担较重的模块

## 例子：对原 TruthValue 类进行 TypeScript 风格改造（超细化流程）

以下流程复盘了完整落地过程，包含所有已知容易偏离目标的风险点与规避方法。后续转写其他代码时，可以参考此流程，避免跨步导致回退或遗漏。

### 0. 立项与范围确认

1. 确认目标是“彻底去 jree 与 Java 语义”，并明确不做目录重构。
2. 明确改造范围：`TruthValue` 本体 + 其调用点 + 关联转换逻辑 + 行为测试。
3. 定义“成功标准”：
   - 行为测试全部通过。
   - `TruthValue` 无 Java 语义残留（clone/hashCode/Serializable 等）。
   - 调用点不再使用旧式 `get/set`。
   - 低层不依赖高层 `Term`（已先迁移）。

风险与规避：

- 目标不清晰会导致“既想保留 Java 语义又想 TS 化”的折中实现，最终产生两套 API。
- 范围不明确会把非目标模块拖进来，导致无法收敛。

### 1. 先做依赖剥离，切断实体层对语言层的耦合

1. 定位 `TruthValue` 中对 `Term` 的依赖：`toWordTerm/fromWordTerm`。
2. 将其迁移到同目录新文件，采用“原名 + 后缀”原则：
   - 从 `TruthValue.ts` 移出到 `TruthValueTerm.ts`。
3. 仅在高层调用端显式引入新文件：
   - 更新 `InternalExperience`、`Believe` 调用点。
4. 确保 `TruthValue` 本体不再 `import Term`。

风险与规避：

- 如果不先剥离，后续去 jree 时会被 `Term` 或 `Symbols` 运行期错误阻塞。
- 若在实体层保留隐式 `Term` 依赖，会导致后续“实体层不得依赖语言层”的原则失效。

### 2. 先写测试，锁定行为

1. 新增 `test/node/truthvalue.test.ts`，覆盖核心语义：
   - 构造与工厂方法的字段映射。
   - `confidence` 截断（TRUTH_EPSILON）。
   - `getExpectation` 公式。
   - `isNegative` 判断。
   - 字符串键 `toKey` 的稳定性与 Map 使用。
2. 测试中只用 TypeScript 语义，不引入 Java 结构。
3. 测试用例只依赖 `Parameters` 与 `TruthValue`，避免引入复杂依赖。

风险与规避：

- 不先写测试会导致“改造成功与否”无法判定。
- 测试范围太广会拉入未知依赖，导致测试因外部原因失败。

### 3. 先落地 API 设计再动实现

1. 约束构造方式：
   - 仅保留“字段一一对应”的构造函数。
   - 其余构造逻辑改为具名工厂：
     - `fromParameters`
     - `fromFrequencyConfidence`
     - `fromTruthValue`
2. 规划字段访问策略：
   - 有逻辑的字段保留 getter/setter（如 `confidence`）。
   - 无逻辑字段改为 public 字段（如 `frequency`、`analytic`）。
   - `narParameters` 只读。
3. 明确替代 Java 语义：
   - `hashCode/equals/clone/Serializable` 全部移除或替换为 `toKey()`。
   - `StringBuilder/CharSequence` 改为字符串拼接。

风险与规避：

- 若不先定 API，会出现“边改边换接口”的混乱，调用点无法统一。
- 若保留旧 `get/set` 与新 public 字段并存，会造成双 API 长期共存。

### 4. 纯 TS 重写 TruthValue

1. 移除 `jree` 依赖、Java 接口声明和类型别名。
2. 实现 `toKey()` 字符串键（替代 hashCode）。
3. 内联 truth 格式化逻辑（避免 `Texts`/`Symbols` 的运行期副作用）。
4. 保留 `confidence` 截断逻辑，确保符合 TRUTH_EPSILON。
5. 不保留 `clone/hashCode/equals`，保留 `fromTruthValue` 或 `clone` 的 TS 替代。

风险与规避：

- 保留 `Symbols` 导致运行期报错（静态初始化依赖 `IN/OUT/ERR`）。
- 直接使用 `Texts` 可能引入额外 Java 类型依赖。

### 5. 全量替换调用点（最容易出错的阶段）

1. 批量替换 `new TruthValue(...)` 为工厂调用：
   - `new TruthValue(f, c, params)` → `TruthValue.fromFrequencyConfidence(f, c, params)`
   - `new TruthValue(f, c, true, params)` → `TruthValue.fromFrequencyConfidence(f, c, params, true)`
   - `new TruthValue(params)` → `TruthValue.fromParameters(params)`
   - `new TruthValue(other)` → `TruthValue.fromTruthValue(other)`
2. 注意参数顺序：`fromFrequencyConfidence(f, c, params, analytic)`。
3. 处理 `clone` 调用：
   - 若仍需要，改为 `TruthValue.fromTruthValue(...)` 或保留 `clone()`。
4. 全量替换旧式 `getX/setX` 调用：
   - `getFrequency()` → `.frequency`
   - `getConfidence()` → `.confidence`
   - `getAnalytic()` → `.analytic`
   - `getNarParameters()` → `.narParameters`
   - `setConfidence(x)` → `.confidence = x`
5. 确保 `confidence` 截断逻辑通过 setter 保留。

风险与规避：

- 自动替换容易引入错位（例如 `fromFrequencyConfidence(narParameters)`）。
- 忽略 `clone()` 会导致部分逻辑引用旧对象。
- 只替换一部分调用会出现“混用旧 API”的长期不一致。

### 6. 运行期阻塞修复

1. 若测试运行时报 `Symbols` 相关错误，立即断开 `Symbols` 依赖。
2. 用常量替代：
   - `TRUTH_VALUE_MARK` = `%`
   - `VALUE_SEPARATOR` = `;`
3. 不要在此阶段引入新的依赖，以免测试失败。

风险与规避：

- 如果在测试阶段仍依赖 `Symbols`，会因为静态初始化报错而无法跑通。

### 7. 测试回归

1. 运行 TruthValue 测试：
   - `node --test --experimental-strip-types test/node/truthvalue.test.ts`
2. 若失败，先检查：
   - 参数顺序是否错误。
   - `confidence` 截断逻辑是否保留。
   - 是否仍有旧式 `get/set` 残留。

风险与规避：

- 不跑测试就继续下一步，导致偏差累积。
- 只修“测试失败”而不修“语义偏差”，会导致后续异常难以追踪。

### 8. 字段访问最终定型

1. 无逻辑字段保留 public：`frequency`、`analytic`。
2. 有逻辑字段保留 getter/setter：`confidence`。
3. 只对内部间接赋值字段使用 `!`（如 `_confidence`），避免滥用。
4. `narParameters` 保持只读字段。

风险与规避：

- 滥用 `!` 会掩盖真实初始化问题。
- 过度 getter/setter 会把 Java 风格又带回来。

### 9. 文档与流程归档

1. 在 spec 里记录通用方法文档入口。
2. 在报告中记录改造过程、测试命令与已知限制。

风险与规避：

- 未归档会导致后续复用困难。
- 未记录限制会导致后续排查成本飙升。
