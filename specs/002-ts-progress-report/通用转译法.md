# 通用转译法（Java → TypeScript）

以下内容总结了在 opennars-304 的转译中发现的系统性差异及对应的解决策略，供 `progress.md` 引用。为避免重复，所有文件的路线图在最后一步均指向本份“通用转译法”中相应的小节。

## 1. Control & Scheduling（控制与调度）
- Java 依赖 `synchronized`、`wait/notify`、`Thread` 定时循环；TS 必须拥抱事件循环与 Promise。
- 建议：抽象 `Scheduler`，用 `setImmediate`/`setTimeout` 驱动一个可暂停的 `async` 循环，所有 Bag/Memory 操作通过消息传递。
- 重点文件：`control/*`, `main/Nar.ts`, `NarNode.ts`, `Shell.ts`, 以及任何实现 `Timable` 的类。

## 2. Entity & Serialization（实体与序列化）
- Java 的 `Serializable`、`clone`、`equals`、`hashCode` 需要在 TS 中重新定义。
- 建议：值对象使用 `readonly` 字段和 `copy()` 工厂；`long` 对应 `bigint` 或 `{ high, low }`；集中实现 Stamp/UUID/TruthValue 的比较逻辑。
- 重点文件：`entity/*`, `storage/Memory.ts`, `storage/Bag.ts`, `language/*` 中的基础类型。

## 3. Inference Rules（推理规则）
- Java 版本依靠静态表、重载方法（`TruthFunctions`, `RuleTables`, `BudgetFunctions`），在 TS 中需要纯函数与类型约束。
- 建议：用 `const` + `Record` 重建所有数组/常量，利用 `type` 限定参数；对关键函数撰写 `node:test` 回归用例，验证数值误差。
- 重点文件：`inference/*`, `operator/*` 中涉及真值或预算函数的操作。

## 4. Interface Contracts（接口规范）
- Java 接口拥有默认方法、多继承；TS 需要 interface 或 abstract class 来表达。
- 建议：每个 Java 接口在 TS 中对应一个 `.ts` 文件，导出 interface/abstract class，并要求实现者显式 `implements`；通过类型别名模拟泛型限定。
- 重点文件：`interfaces/*`, `operator/Operator.ts`, `plugin/*`。

## 5. IO & Event Pipelines（I/O 与事件）
- Java 继续使用 `java.io.*`、`Observer`/`EventListener`；TS 应转向 Node `Readable`/`Writable`、`EventEmitter`。
- 建议：Parser/Narsese 采用生成器或 `for await...of` 实现流式解析；EventEmitter 中的 handler 需要具名类型、解除反射依赖。
- 重点文件：`io/*`, `io/events/*`, `plugin/perception/*`.

## 6. Language Layer（语言层）
- Term/Statement/CompoundTerm 等类 heavily 使用 Java 泛型、静态缓存。
- 建议：使用 TS 泛型 + `readonly` 属性表达层次；缓存统一放入 `Map<string, Term>`，暴露工厂函数以便测试替换；equals/hash 逻辑需要集中单元测试。
- 重点文件：`language/*`.

## 7. Main Runtime（主程序）
- `Nar`, `NarNode`, `Shell` 依赖 Java 线程、CLI、Socket；TS 需要 Node runtime 适配。
- 建议：封装 `NarRuntime` 入口，拆分 CLI 解析、参数渲染、worker 启动；用 async 函数暴露生命周期，便于测试注入。

## 8. Operators（操作符）
- Java 中 Operator 通过反射注册 Operation；TS 应显式描述依赖和副作用。
- 建议：实现 `OperatorRegistry`，在构造时注入 `Memory`、`Task` 等；操作符返回 Promise 以兼容异步场景，并提供最小 mock 测试。

## 9. Plugins（插件）
- Java 使用 `ServiceLoader` 或反射加载插件；TS 中需显式工厂。
- 建议：所有插件接入统一的 `PluginContext`（包含 EventEmitter、Memory 引用、配置），实现 `start()/stop()`；感知通道用 `AsyncIterable` 处理输入数据。

## 10. Storage Structures（存储结构）
- Bag、Memory、Distributor 需要保留容量控制与优先级行为，同时脱离 Java 的同步块。
- 建议：使用纯函数/类模拟容量计算，按需使用 `BinaryHeap` 或 `bucket queue`；暴露调试日志以检验 order/pick 等行为；加强 Node 测试（目前只有 Distributor 有测试）。

## 11. Util Layer（工具层）
- Java `java.util.*`、`Collections`、`Arrays` 提供大量工具；TS 需要轻量替代。
- 建议：集中在 `util/` 提供 list/array/number 工具，写足断言以弥补 Java 的防御式编程；明确 `int` 与 `long` 的取值范围假设。

## 12. Testing & Tooling（测试与工具链）
- 目前仅 `storage/Distributor.ts` 有 node:test。所有核心模块都缺乏验证。
- 建议：每个包至少补充 smoke test，验证主要 API；`npm test` 需要扩展至所有新增测试文件；在 CI 中以 `npx tsc --noEmit` + `npm test` 为准。

> 使用方式：`progress.md` 中的每个文件段落列出“路线图”三步，第三步引用上述小节，确保所有 Java→TS 差异被归档并复用。
