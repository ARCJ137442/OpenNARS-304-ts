## 任务过程笔记

- Java `float` 的关键不是表达式末尾统一 `Math.fround`，而是保留 Java 源码中变量声明、显式 cast 和赋值边界；两个 `float` 操作数必须先收窄再运算，否则 1 ULP 差异可能改变 Bag level、取出顺序和后续规则派发。
- 当前最小修复仍直接写在已证实的两个推理引擎边界，避免把所有 Number 运算机械替换为 `fround`。下一阶段可以从这些边界提炼 `Float32` 转换/计算函数，先用 Java/TS 局部快照覆盖，再决定是否引入专门的 `Float32` 类型；它的成立前提是先枚举 Java float 语义边界，并确认封装不会隐藏原始算法的赋值时机。
- 模块循环的可靠解法不是继续增加静态 import，而是把初始化责任沿“数据结构 → 容器 → 推理规则 → 推理引擎 → 入口”分层；规则层只依赖类型或运行时登记，入口层在所有实现类完成加载后注入运行时表。
- runner 的最终验收不能把“Java/TS 同时没有 marker”当成功；`matched`、`functional_pass`、异常、超时和 marker 缺失必须独立保存。逐文件进程也让一个高成本 NAL 不再阻塞整批结果。
- 短超时矩阵是差异分类证据，不是全量等价验收。特别是 TS 超时多于 Java 时，首先需要区分启动/性能成本和真实语义差异，不能用 timeout 行替代 marker 结果。
- 当前 LeanSpec CLI 仍因全局安装缺少 `lean-spec.js` 而不可用；按新的项目政策只读保留 `013`，不伪造新 spec、不手工改 frontmatter，业务修复继续在当前里程碑下推进。
