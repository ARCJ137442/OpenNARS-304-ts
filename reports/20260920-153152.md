## 下一系列修改与决策顺序

```text
J4-operator-plugin
  1. Statement relation factory / exception / text contract
     -> 先补 Java/TS 多态输入与异常测试，再拆最小 native 边界
  2. Operation / mental operator 剩余 Java String 输入
     -> 只在确认没有 identity/hash/overload 依赖后收窄
  3. plugin constructor / lifecycle boundaries
     -> no-arg、boxed input、异常和事件 payload 分开验证

J1-runtime-compat（与 J4 交叉但不混为一谈）
  1. isJavaThrowable / runtimeLong / javaStringValue 的剩余调用者盘点
  2. javaStringHashCode 与领域 Map/Set key 合同
  3. 仅在调用者合同闭合后收窄 jree-compat.ts；不做全局替换

J2-language/parser
  1. 复合项工厂的 null 合同（Difference/Disjunction/Intersection/Negation/Similarity 等）
  2. Statement/Term 的 class identity、重载和初始化环
  3. 数据结构按真实语义保持 List、Map、Set、排序集合；数组只用于已证明的临时顺序缓冲

J3-inference core
  1. 继续审查历史 NativeList/数组化提交，逐个回到 Java 声明确认原类型
  2. Map/Set 的 equals/hashCode、迭代删除、插入顺序和 null 边界
  3. 簇闭合后才运行一次 M1-，避免每个局部切片重复消耗全量资源

J5-main/host -> 024
  1. 把 Node 文件系统、stdin、process 与核心推理边界继续外移
  2. 形成 platform-neutral core 与 host adapter 的接口证据
  3. 023/024 阶段门禁执行 live Java + full M1 + 严格 markerless evidence
```
