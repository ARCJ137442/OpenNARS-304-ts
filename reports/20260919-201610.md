### 下一系列修改

1. **J3：NativeMap 领域对象 key 与恢复态边界。**
   `CompositionalRules`、`CompoundTerm.countTermRecursively`、`Variables`、`SyllogisticRules` 和 `Anticipate` 仍有 `java.util.Map` 外形或 NativeMap 强制转换。先按 Java 声明和调用链逐项分类：替换映射、计数 Map、预测 Map、私有累积器不能混为同一类。优先处理没有公共 Java API 泄漏的私有 Map；涉及 `Term`、`Operation`、`Prediction` 等领域对象 key 时，先补 equals/hashCode、插入顺序、live view、迭代删除和恢复态合同，再做局部原生化。
2. **J3 前向审计：历史 List/数组替换。**
   对更早提交逐项回到 canonical Java 声明，核对 List、Set、Map、排序集合、数组和 builder 的语义。已有 `CompoundTerm.extractIntervals` 的 List 契约恢复说明“调用者能用数组”不能替代公开类型；后续只在 Java 明确是数组且没有集合行为时收窄为数组，并在代码注释中保留原类型与原因。
3. **J1：拆分 jree-compat 的职责边界。**
   `src/runtime/jree-compat.ts` 当前集中承载 Java String/CharSequence、long 转换、Float/Double 包装、异常类型、日志、DecimalFormat、Runtime、StringJoiner、Java equals/hash 和宿主退出等桥接。先将纯值语义与 Node/宿主能力分开，逐个把可由 TS 原生表达的合同迁出；异常、日志、进程退出和宿主能力仍保留窄桥，不以“删除 import”代替行为验证。
4. **J2、J4、J5：按依赖顺序收口。**
   J2 处理语言/解析层残余，J4 处理 operator/plugin，J5 处理 Nar/CLI/宿主入口。每个小簇沿数据结构→容器→推理规则→推理引擎→程序入口推进；局部簇采用直接合同、串行 M2 和 2～5 个受影响 NAL，责任簇收口才运行一次 M1-。024 的 P3～P5 与 023 分开验收，集成门禁再共同运行 245+1。
5. **验证与性能边界。**
   日常切片继续复用冻结 Java 标杆，不重复启动 Java；只有 Java artifact、整项 spec 或集成验收才现开 Java 并确认三次存档一致。M1- 和长期 #245 不作为每个局部修改的默认门槛。TS 单线程功能稳定后，再使用已有运行时长/推理周期、峰值 RSS 和 marker 时间戳做 020 性能优化；性能警告不掩盖逻辑分叉。
