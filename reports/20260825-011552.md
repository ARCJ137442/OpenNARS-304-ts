## 已确认事实

- Java `Term` 有一个 protected 无参构造器和一个 public `Term(CharSequence)` 构造器。
- 当前 TS 以 public `constructor(CharSequence)`、protected `constructor()` 和 protected implementation 混合表达，触发 `TS2385`；外部带名调用回落为 protected 实现并触发 `TS2674`。
- TypeScript 没有 Java 的包级访问控制，Java 源码中跨包/同包调用的构造器访问不能直接用 protected 表达。
- 本批前基线为 1698 项：生产 759、测试 939。

## 假设、实验与结论

- 先把调用点的静态字符串包装为 `S`/`new java.lang.String`/`String.valueOf`，但诊断仍为 1698；这证明单纯改调用点不能修复重载可见性。
- 给 `Term` 增加 `java.lang.String`、再改为显式 `JavaString` 重载，分别仍保留 `TS2674`，并增加 overload 可见性诊断；这些声明实验不单独保留为最终方案。
- 最小有效修复是把 `Term` 的无参 overload 与 implementation 统一为 public，同时保留 public 带名 overload；这只扩大 TypeScript 的构造入口，不改变构造逻辑或 Java 命名构造器行为。
- 修复后诊断为 1688：生产 749、测试 939，减少 10；除独立的 `InputThread` 外，相关 `Term` `TS2674` 消失。

## 任务过程笔记

- 这里的关键不是“把 protected 全部改 public”，而是 TypeScript overload 签名必须统一访问级别；public 带名构造器与 Java protected 无参构造器不能在同一组 TS overload 中保持 Java 的包级语义。
- 构造逻辑仍按参数数量分派，无参和带名路径未重写；公开无参入口是类型系统边界适配，后续应在 API 文档中说明其“内部构造”性质。
- `Nar.ts`、`VisionChannel.ts` 和相关测试保留其原有修改/残余诊断，本批没有通过修改它们来制造更大的变更面。
