## 下一系列修改的推导与顺序

### 第一组：完成 J1 异常捕获观察面

先审查 `Shell.ts`、`Operator.ts`、`Nar.ts`、`NarNode.ts`、`TextOutputHandler.ts`
中 `instanceof java.lang.Exception/Throwable` 的真实捕获用途，补齐原生异常、消息、
cause、stack 输出和未知错误的测试。随后把各生产者从 `jree-compat.ts` 的异常再导出
迁到 `JavaExceptions.ts`，最后才删除对应的 `Symbol.hasInstance` 注册项。顺序是：

```text
异常生产者 → 捕获/格式化消费者 → 直接回归 → 受影响 NAL → 删除桥接责任
```

不能先删桥再修捕获端；否则会把“逻辑没错但异常没有被 Java 捕获面观察到”误判成普通
功能通过。

### 第二组：J3 `introduceVariables` 嵌套 Set/Map

回读 canonical Java 的局部声明、调用者和 `equals/hashCode`，确认变量候选的 Set、
替换 Map、迭代删除和插入顺序，再决定使用 `NativeSet`、`MapContract` 还是保留边界。
先补直接合同，再跑 2～5 个覆盖变量统一和规则派发的 NAL；不把嵌套 Set 的底层数组
实现误写成 List 语义。

### 第三组：J2/J3 历史前向审查与簇收口

继续审计早期 List→数组、Set→List、Map→普通对象和 `StringBuilder`→字符串模板的
提交。每个点都写明“Java 原类型 → 当前 TypeScript 类型 → 依赖的调用面”；只有 Java
合同证明允许时才使用原生数组或模板字符串。J2/J3 各自完成后，才运行一次串行 M1-；
责任簇未收口的 T1 批次不重复运行整矩阵。

### 第四组：J4/J5、024、集成和发布

J4 处理 operator/plugin 的字符串、异常和反馈边界；J5 处理 Nar/Shell/Node 能力与
退出副作用；024 P3-P5 处理浏览器/宿主适配。之后在同一不可变提交运行 live Java、
冻结标杆、M1/M1-、M2、CLI/API、浏览器和覆盖率证据，最后才进入性能正式门、bundle、
RC 和 tag。

## 修改内容汇总

### `src/runtime/JavaExceptions.ts`

- 扩展项目内 Java 异常层级和缺失的 checked-exception 类型。
- 增加 Java 风格 `printStackTrace` 输出边界。
- 目的：让异常身份、消息和 cause 脱离 jree，同时保留当前观测契约。

### `src/runtime/jree-compat.ts`

- 将异常类由本地 jree 子类改为项目异常导出。
- 增加带原始判定保留的 `Symbol.hasInstance` 过渡注册。
- 目的：兼容旧 catch/`instanceof` 调用面，并为后续逐项删桥提供明确边界。

### `test/node/java-exceptions.test.ts`、`test/node/runtime-compat.test.ts`

- 增加异常族继承、消息/cause、jree 旧观察面的直接回归。
- 目的：防止后续迁移只通过 TypeScript 类型检查，却丢失运行时异常语义。
