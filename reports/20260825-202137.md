## 任务过程笔记

- 已证实：M3 观测必须区分“runner wall time”和引擎子进程的 wall/CPU/RSS；否则 Java adapter 编译和进程启动会污染推理耗时。
- 已证实：TS 正式 dist 可以直接通过 `process.resourceUsage()` 和 `process.memoryUsage().rss` 提供 per-file 观测；Java 标准管理接口能提供进程 CPU，但不能在当前适配器中直接提供 Windows RSS。
- 当前选择：资源采样是显式开关，避免日常功能回归改变运行成本；checkpoint run key 包含该开关，避免复用无资源字段的旧结果。
- 未证实：Java committed virtual memory 是否能作为 RSS 的替代。报告只称其为 proxy，不参与跨引擎 RSS 结论。
- 已验证候选边界：jree `JavaObject` 堆栈热点可在兼容层预置继承标记后跳过；仍需以固定提交上的正式 benchmark 作为最终保留依据。
- 已确认优化：在当前锁定的 jree 1.3.0 中，`"#fqn"` 只被 `JavaObject` 构造函数写入，`Class` 和 OpenNARS 不读取；兼容层预置继承标记可跳过死的堆栈解析路径。固定 commit 上的类身份回归和两个 NAL 样本均通过。
- 新增事实：资源 benchmark 的 `git_commit`、canonical JAR 哈希和每次运行的 marker/资源字段都已写入 `reports/evidence/m3-formal-resource-baseline-20260825-nal8-v1.json`；该文件的 p95 在单次重复时等于该次观测，不应当解释为稳定分位数。
- 固定提交的正式优化证据分别写入 `reports/evidence/m3-formal-resource-baseline-20260825-nal8-fqn-v2.json` 与 `reports/evidence/m3-formal-resource-baseline-20260825-toothbrush-fqn-v2.json`；两份文件的 `git_commit` 均为 `4d5435f630cf1341b8f0a8236d7ccee40413ed50`，p95 仍只代表单次观测。
