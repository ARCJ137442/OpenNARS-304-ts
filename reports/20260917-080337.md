## Java 合同与设计决策

Java `eventInference` 中 `already_attempted` 与 `already_attempted_ops` 只进行 `contains`、`add`、`clear`；Java 的 `LinkedHashSet` 还保留插入顺序。`Task.equals` 按 Sentence 值判等，因此原生集合必须同时满足：Set 的唯一性、Java 值判等和稳定迭代顺序。`NativeSet` 与 `NativeList` 分离，即使当前底层都使用数组，后续 Set 存储优化也不会改变调用点语义。

本次回溯审计的结论是：

- `NativeList` 的已提交使用点均对应 Java `List`/`ArrayList` 的索引、追加、结果缓冲或只读视图；`Conjunction` 等局部变量虽旧名为 `set`，Java 声明实际是 `List`，不属于 Set 错配。
- `NativeSortedSet` 对应 `Term.toSortedSet` 的 `TreeSet` 语义，排序比较器和去重边界不能降为普通数组。
- `NativeDeque` 对应 `Deque` 的 FIFO 与迭代器删除；`EventEmitter.pendingOps` 的数组仅是私有 FIFO 队列，清空时机和事件顺序保持。
- 原生 `Map` 的已迁移点（符号/时态文本索引、操作符注册、原子缓存、变量重命名）都将 Java 对象键收窄为明确文本键，并在读取处处理 `undefined → null`；`Bag.itemOrderIndex` 明确是私有对象身份索引，不替代 `nameTable` 的 Java equals 键语义。
- 既有字符串缓冲暂未做无证据的批量替换。后续只有在确认“纯拼接、无 Java StringBuilder API 观测”的调用点后，才可改为模板字符串，并必须在调用点注明 Java 来源与文本顺序/格式契约。
