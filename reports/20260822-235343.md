## 任务过程笔记

- jree 运行时不是透明的 Java 语义层：Java String、StringBuilder、boxed Long、JavaObject 和延迟修改的 Charset 都可能在 JS 边界表现为不同对象。兼容逻辑应集中在 `src/runtime/jree-compat.ts`，而不是修改 `node_modules` 或在各业务模块重复猜测。
- Java 的重载和 varargs 不能仅按 TypeScript 的静态签名迁移。必须先按 Java 的运行时参数形状分派；本批 Image、Product 和 Operation 的差异都由此产生。
- `matched`、功能通过、异常、超时和 marker 缺失必须独立记录。短预算矩阵适合定位分层差异，不适合替代全量功能验收。
- Java float 的操作数收窄与 TypeScript Number 的双精度计算仍是数值边界风险。局部算法快照在 `1e-5` 容差下通过，但这只证明当前快照，不证明所有调度/排序路径已经完成 Float32 语义迁移。后续如出现可复现的数值分叉，应把收窄、计算和格式化聚合成可测试函数，再评估专门的 Float32 类型。
- 高成本 NAL 暴露了当前主要瓶颈是 TS 推理链收敛/运行时间，而不是本批已修复的初始运行时异常。下一步应在有分段轨迹的前提下定位首个语义或调度分叉，不应直接放宽验收口径。
