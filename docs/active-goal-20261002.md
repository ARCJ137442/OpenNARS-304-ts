### 1. 原生化与架构

- 维护源码、构建入口、发布包与运行时不依赖 npm `jree`，不再通过 `import { java, ... }` 或改名的 Java namespace 绕回同一机制；`audit:jree`、依赖树和产物扫描都要为零。
- `src/main`、语言、推理、存储等核心模块不导入 Node/浏览器实现。文件、终端、时钟、序列化、网络等由窄的宿主能力注入；Node CLI 与浏览器 Worker 从 `src/platform` 装配。公共 API 暴露领域对象与原生 TypeScript 类型，不泄漏宿主或 jree 类型。
- 清理 Java 转写留下的偶然形状：多余的 boxed 值、反射壳、一次性 StringBuilder、机械重载、字符串拼接、异常别名与可用原生迭代替代的代码。保留有证据的合同：UTF-16、字符串 hash/比较、float32/long 边界、随机序列、相等方向、集合顺序与可变迭代器、异常分类、事件/操作身份。每次修改要说明“原 Java 为什么需要它、TypeScript 中真正的领域意图是什么”。
- 只做有独立变化理由的抽象与合并；让人用 VS Code/Zed 阅读核心、修改一个推理规则或增加一个宿主入口时，不必先理解 Java 兼容命名空间。遵循 `arc137-dev-standard` 与仓库 `AGENTS.md`。

### 2. 性能及 Demo 的可观察目标

- 固定提交、Node/浏览器版本、输入、周期数和随机条件，分别记录推理 RPS、世界 TPS、画面 FPS、实际/目标 TPS、step 中位/p95、概念与任务袋规模、Worker 队列、内存/RSS。FPS 不替代 TPS，异步 TPS 不冒充推理器 RPS。
- 优先处理 CPU profile 和概念增长证明的热点，包括 `Bag` 查找、词项判等、runtime 转换、分配与 GC 长尾；只有测量和直接合同支持时才用原生 TypeScript 路径替换迁移绕路。推理器和 Demo 调度分别比较同条件 A/B，不以牺牲 NAL 结果、操作顺序、可读性换吞吐。
- 用户期望 Microworld 持续实际 TPS 达到 20 以上；其他同步 Demo 的实际 TPS 争取达到目标 TPS 的至少一半，进一步争取 15 以上。RPS 至少稳定高于 1，并持续改善长尾。未达到的数值必须如实列出，不得把设定的目标 TPS 或短时峰值写成持续实测。
- 每个 Demo 都能看到 FPS/TPS/RPS；性能追踪以渐进披露展示内存、概念袋、队列、延迟与操作。同步/异步模式的环境时钟语义明确。Microworld、Pong、CartPole、TicTacToe 等入口需实际运行；关键 Demo 至少出现随环境变化由 NARS 发出的非 babble 操作，并可在日志追溯感知、目标与操作。Demo 仍须保持可维护的 TypeScript/Astro 静态构建和正确画面。
- 优化采用连续轮次：每轮以事先指定的主要指标和同配置复测判断；任何功能/语义回退直接否决。达到连续三轮各主要指标收益均小于 5% 且再无有根据的高收益候选，才可称“本阶段性能收敛”。若仍未达到 TPS 期望，必须解释剩余瓶颈与限制，不能说性能目标已实现。
- 性能发布条件为达到实测 TPS 目标，**或**完成上述收敛证明并在网站/发行说明显著披露仍未达到的目标；两者都没有证据时不进入新 fix release。短测 A/B 本身不是 Demo 持续流畅性的证明。

**测量口径和停止规则：**

1. 每个候选先写明要改变的热路径、受保护的语义合同、主指标、对照配置及失败时撤销条件，再做同机器、同输入/seed、同周期和同 Node/Chrome 版本的基线→候选→候选复测。报告绝对值、百分比、p50/p95、RSS/页面内存、概念数和任务/操作数；只有跨复测稳定且无语义回退的收益才算有效。
2. 短 Node 负载用来筛选推理器候选；真实浏览器至少观察 30 秒，并看分段窗口、最后窗口、概念增长和长尾。Microworld 的 20 TPS 是**持续实测的世界步进**要求，不是设定值、画面 FPS、初始峰值或异步模式的表面流畅。其他同步 Demo 先检验实际/目标 TPS ≥ 1/2，再争取 ≥ 15 TPS。记录 RPS 的计数方式和实际 NARS 周期数，不能把 Worker 空闲或排队时间抹掉。
3. 性能优化覆盖推理器与 Demo 两条链：先判明瓶颈来自核心计算、概念/任务增长、GC/内存，还是环境输入与同步等待；环境降采样、减少 NARS 周期或关闭日志若改变学习条件，应列为单独的行为实验，不能算作同语义优化。异步测试必须同时记录世界刻和**实际完成**的推理步长、待处理时长、迟到操作与概念变化；世界 TPS 达标而 NARS 零进展属于未通过，HUD 不能长期显示陈旧 RPS。
4. 连续三次低收益只从**最后一次被接受的 >5% 优化之后**开始计数，每次都须针对仍然明确的主要瓶颈且有可复现的对照；明显未测的高收益假设存在时不得宣称收敛。任何一轮稳定收益 ≥5% 会重置计数。最终若仍低于 TPS 目标，需明确写出达到的持续值、未达到的差额、残余热点和继续优化的建议。
5. 每个纳入公开 Lab 的 Demo 必须能加载、开始/暂停/重置并真实运行 NARS；至少提供可复现的环境变化场景，观察到由 NARS 自主发出的非 babble 操作，记录感知→目标→推理→操作→环境反馈的证据。若个别 Demo 未达到，不能用画面或随机 babble 假装已接入学习闭环；发布前修复或明确降格为实验入口。

### 3. 测试与证据门

- 日常先跑直接合同、非增量 typecheck、build/dist API、TS-only M2 和受影响 NAL；已有同提交、同输入、同预期的 NAL 证据可复用，避免重复运行。阶段收口在同一不可变提交上核对 M1′、含 Java 的完整 M2、strict markerless、Node CLI/API、真实浏览器 Demo、依赖/平台/编码审计。
- PC 的 M1′ 使用 243 项保护矩阵，另核对 #25 和 #246；#245 `long_term_stability` 单列为降周期实验。先用 2048 周期估算 65536 周期，估计 ≤1200 秒才运行，安全上限 1800 秒；原始 2,000,000 周期遇到持续系统瓶颈时明确标为未完成。不得把 `process_limit`、`timeout`、`exception`、`stall`、`not_run` 写成通过。
- Java 冻结 baseline 已有独立一致性证据时不重复启动 canonical Java；确实改变可观察语义或最终阶段门要求时才现跑。长测单进程、唯一前缀、逐文件 checkpoint、可恢复，监测 RSS，避免再次触发内存故障。
- 证据记录源码 SHA、工作区状态、配置、退出状态、耗时与资源指标；结论区分“已测通过”“预计”“未测”“资源限制”。不删除历史未跟踪证据，也不使用 `git add -A`。
