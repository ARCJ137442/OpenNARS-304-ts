# OpenNARS-304-ts 新战略基线与工作流

版本：v2.0（2026-08-21）

本文件取代旧的“按文件逐个转写”规划，作为当前项目的战略导航文档。旧规格、旧报告和 `specs/003-dependency-analyze-brief-plan/workflow/roadmap.md` 仍是历史证据，但不再单独作为当前排期依据。

## 一、先定项目到底要成为什么

### 最终目标

在 Node.js/TypeScript 环境中，形成一个可运行、可测试、可维护、行为上尽可能等价于 OpenNARS 3.0.4 Java 核心的 NARS 推理内核。

“完成”必须同时满足四个条件：

1. 工具链可重复：新环境可以安装依赖、编译、运行测试。
2. 主链可运行：可以输入 Narsese，经过 Memory 和推理循环，产生可观察输出。
3. 行为可验证：关键结果能与 Java 基线或 NAL 资源进行差分比较。
4. 架构可持续：Java 语义被明确替代，模块边界、导出面和测试边界稳定。

文件存在、Java 路径映射存在、局部测试通过，都只能证明局部进度，不能证明项目完成。

### 目标分层

| 层级 | 目标 | 当前判断 |
|---|---|---|
| G0 | Java 来源、依赖、工具链和分支状态可复现 | 未完成 |
| G1 | 最小 NARS 垂直切片可运行 | 未完成 |
| G2 | 语言、实体、存储、I/O 和推理核心逐层闭合 | 局部完成 |
| G3 | 核心 NAL 行为与 Java 基线对齐 | 未验证 |
| G4 | 插件、主循环、稳定性、性能和扩展能力完善 | 未开始系统验收 |

近期唯一主攻目标是 G1：先跑通一条最小但真实的 NARS 主链，而不是继续增加孤立的 TS 文件数量。

## 二、当前事实基线

调查依据：当前 `main` 工作树、Java 基线仓库、`git` 历史、`specs`、`reports`、现有测试与可执行命令。

- 当前 `main` HEAD 为 `8299bab`（2026-02-05），主线比 `origin/main` 超前 1 个提交。
- `src` 有 121 个 TS 文件、约 21,759 行；`test` 有 34 个测试文件、约 2,608 行。
- Java 生产代码有 119 个类文件，`ts-analysis.json` 映射 119 个；另有 `types.ts` 和 `TruthValueTerm.ts` 两个 TS-only 文件。
- Java 基线保留 30 个测试文件和 246 个 NAL 资源文件，这是后续差分测试的主要资产。
- 当前 `npm test` 只执行 Distributor 测试；TruthValue 和 Texts 测试需要手工指定。
- 当前仓库没有本地 TypeScript 依赖；全量 `npx tsc --noEmit` 不能作为当前编译验证。
- 当前绝大多数 TS 源文件仍依赖 `jree`，或保留 Java 集合、重载、内部类、线程、序列化和反射语义。
- TLink 已在当前主线；Stamp 纯 TS 改造只存在于 `vk/17da-stamp`，不能直接视为主线完成。
- 规格 005、008 仍是 `in-progress`，并存在未完成的测试/计划项。
- `java-master` 是 Windows 目录符号链接，而来源标注脚本按文本指针处理；`ts-analysis.json` 还保留失效的临时绝对路径。

### 架构主链

```text
Narsese / Parser
    ↓
Term / Sentence / TruthValue / BudgetValue / Task
    ↓
Bag / Concept / Memory
    ↓
GeneralInferenceControl / DerivationContext
    ↓
RuleTables / TruthFunctions / BudgetFunctions / TemporalRules
    ↓
Derived Task → Memory → Event / Plugin / Output
    ↓
Nar.addInput / Nar.cycle / Nar.ask
```

这条链是排期的依据。模块只有在它的下游依赖已闭合时才进入集成，不再以目录名称或文件数量作为完成标准。

## 三、旧规划为什么失效

旧规划有价值的部分：

- 要求阅读 Java 来源。
- 要求分析 TS 依赖和 Java 依赖。
- 要求区分结构性依赖和表面依赖。
- 要求先测试、再转写、再回归。
- 要求记录来源头和过程报告。

旧规划缺失的部分：

1. 没有把“可运行的 NARS 主链”定义为最高验收目标。
2. 没有定义工具链、ESM、TypeScript 编译器和测试入口的基线门槛。
3. 没有定义模块级闭合条件，只能产生单文件分析记录。
4. 没有定义 Java 与 TS 的差分验证策略。
5. 没有处理主线与并行分支之间的 canonical 状态问题。
6. 没有及时淘汰失效的绝对路径、旧错误统计和过时 README 进度表。

因此，旧路线的根本问题不是“排序不够精细”，而是优化目标错位：它把“翻译活动”当成了“系统交付”。

## 四、问题定义与思考方法

### 项目真正提出的问题

不是“如何把 Java 语法改成 TypeScript 语法”，而是：

> 如何在不改变 NARS 核心行为的前提下，把依赖 Java 运行时、对象模型和线程模型的推理系统，重建为可在 Node.js 中独立运行、可验证、可维护的 TypeScript 系统？

这个问题包含五个子问题：

1. 语义问题：哪些 Java 行为必须保留，哪些只是仪式性代码？
2. 边界问题：模块如何导出、依赖、初始化和组合？
3. 运行时问题：集合、线程、序列化、反射、时间和异常如何替代？
4. 验证问题：如何证明结果不仅能编译，而且和 Java/NAL 行为一致？
5. 工程问题：如何让后续每次转写都能重复、审计、回滚和合并？

### 当前主要矛盾

| 矛盾 | 当前状态 | 当前处理原则 |
|---|---|---|
| 转写广度 ↔ 集成深度 | 明显偏向广度 | 先垂直切片，再扩展覆盖面 |
| Java 保真 ↔ TS  idiomatic | 边界未定 | 先保留行为，逐项替代 Java 仪式 |
| 自动化速度 ↔ 人工审计 | 自动转译遗留多 | 自动化扫描，关键语义人工对照 |
| 并行探索 ↔ 单一主线 | 已出现分支漂移 | 分支可探索，只有过门禁的结果进主线 |
| 短期可运行 ↔ 长期纯 TS | 容易互相争夺 | 先允许临时适配层，但禁止新增隐式依赖 |

主要矛盾是“广度与深度”的失衡。只要打通一条真正可运行的主链，后续模块就有明确的接入标准；继续扩大未接通模块只会扩大级联错误。

## 五、新工作流：集成优先的六步闭环

每个阶段、模块和规格都必须经过下面的闭环。单文件模板只作为其中一个环节，不再是最高层工作流。

### Step 1：发现与定界

输入：当前工作树、最新报告、规格、Java 源码、分支和测试资产。

输出：一页模块合同，至少包括：

- 目标和非目标。
- Java 来源及行为职责。
- 对外导出面。
- 结构性依赖和表面依赖。
- 运行期副作用。
- 直接测试和上游/下游调用点。
- 本阶段的退出条件。

禁止：只看旧报告，不核对当前代码和命令输出。

### Step 2：先定义可观察行为

先选择一个最小输入、最小输出和最小不变量。例如：

- 能解析一条判断、问题或目标。
- 能创建对应 Task/Sentence/Term。
- 能把 Task 放入 Memory。
- 能完成一个 cycle。
- 能收到一个可断言的输出或状态变化。

所有预期值注明来源：Java 常量、Java 测试、NAL 资源、数学公式或当前设计决策。

### Step 3：设计 TypeScript 边界

在实现前明确：

- primitive 类型和整数/浮点约束。
- `Array`、`Map`、`Set`、队列和迭代器替代物。
- 构造重载到工厂函数的映射。
- null/undefined 策略。
- 错误类型和错误传播。
- 时间和随机性注入方式。
- 线程、序列化、反射和文件 I/O 的替代策略。
- ESM import/export 规则。

原则：允许暂时存在显式 adapter；禁止在基础层隐藏高层依赖，禁止新增未经记录的 `jree` 依赖。

### Step 4：实现闭合层并验证

先写行为测试，再改实现。每次只合并一个闭合层：

1. 运行该层的编译检查。
2. 运行该层的单元测试。
3. 运行至少一个上游调用点测试。
4. 运行一个垂直切片 smoke test。

单元测试通过但闭合层无法被上层 import 时，仍视为未完成。

### Step 5：Java/NAL 差分验证

对同一个输入，在 Java 基线和 TS 实现上分别运行，比较：

- 解析结构。
- 任务类型和项内容。
- Truth/Budget 数值。
- 关键时间和证据链。
- 输出事件和答案。

允许存在已记录的运行时差异，但不允许用“TS 更方便”作为未经验证的语义改变理由。

### Step 6：归档、合并与复盘

只有以下证据齐全，才允许标记完成：

- spec 计划和测试项全部完成。
- 编译、单元、集成、差分命令有实际输出。
- Java 来源和依赖记录仍有效。
- README/路线图/报告与当前分支一致。
- 变更在一个可追溯提交中完成。
- 已记录未解决风险和下一阶段入口。

## 六、新路线图与阶段门禁

### P0：建立 canonical 基线

Java→TypeScript 的重复迁移纠正统一记录在[迁移模式库](java-to-typescript-migration-patterns.md)，批量改写必须先经过模式扫描与分级。

目标：让项目的“当前事实”可以被任何后续工作复现。

工作：

- 添加本地 TypeScript 或统一的编译执行方案。
- 明确 package type、ESM import 扩展名和 Node 测试入口。
- 让 `npm test` 覆盖所有当前可运行测试。
- 修正 Java symlink 解析和来源映射的相对路径策略。
- 重新生成映射、模块清单、错误报告和测试清单。
- 明确 canonical main；并行分支必须标注探索、待合并或废弃。

门禁：新环境能安装依赖；`tsc` 命令真实存在；测试入口可复现；来源检查不因路径形式失败。

### P1：打通运行时和模块边界

目标：所有基础模块可以被 Node 正确 import，不在模块加载阶段出现未定义符号。

范围：

- `types.ts`、Parameters、Debug。
- Symbols、Texts 和基础错误类型。
- interfaces、Plugin、Event 基础契约。
- jree 兼容层的边界定义。

门禁：基础模块闭合编译；所有接口显式导出；没有新增隐式全局符号；至少一个基础模块集成测试通过。

### P2：最小语言与实体垂直切片

目标：从 Narsese 输入构建可比较、可打印、可放入内存的 Task。

建议顺序：

```text
Term / AbstractTerm / CompoundTerm
→ 基础复合项与变量
→ TruthValue / BudgetValue / Stamp
→ Sentence / Task / TLink / TermLink / TaskLink
→ Narsese / Parser
```

门禁：判断、问题、目标至少各有一条解析与 round-trip 测试；核心对象可以构造、比较、格式化；与 Java 基线的基本结构一致。

### P3：Storage、Memory 和事件循环

目标：完成从 Task 到 Concept/Memory 的实际状态变化。

范围：Distributor、Bag、Concept、Memory、EventEmitter 和基础输出。

门禁：输入 Task、创建/取得 Concept、完成一次 cycle、产生可观察事件；验证 Bag 分布、容量和优先级不变量。

### P4：推理核心

目标：使一条输入可以经过推理规则产生派生任务。

建议顺序：

```text
UtilityFunctions
→ TruthFunctions / BudgetFunctions
→ TemporalRules
→ LocalRules
→ StructuralRules
→ SyllogisticRules / CompositionalRules
→ RuleTables / DerivationContext
```

门禁：先通过单步 NAL，再通过多步 NAL；每个规则族至少有公式测试、边界测试和 Java/NAL 差分样例。

### P5：Nar 主循环与公共 API

目标：外部调用者可以使用 `Nar.addInput`、`Nar.cycle`、`Nar.cycles` 和 `Nar.ask`。

门禁：Node 下完成一个端到端脚本；不依赖 Java 文件、浏览器或未定义的全局符号；失败输入有稳定错误输出。

### P6：完整性、插件和长期稳定性

目标：扩展到 Java 基线的 246 个 NAL 资源，并处理插件、感知、序列化、性能和稳定性。

门禁：按 NAL 层级统计通过率；长期运行和保存/加载测试有明确结果；性能差异被记录而不是隐含接受。

## 七、并行安排与主次关系

主线必须集中在 P0→P1→P2→P3→P4→P5。以下工作可以并行，但不能绕过主线门禁：

- Java/NAL 差分工具：从 P0 开始建设，服务所有阶段。
- Stamp、TLink 等局部转写：可在 P1/P2 并行，但必须以当前 main 为基线并通过集成测试。
- 文档和来源映射：持续维护，但不能替代运行验证。
- 性能、网络、感知插件：放到 P6，不得抢占 P2/P3 的主线资源。

### 优先级判断

| 工作 | 影响 | 信心 | 难度友好度 | ICE 参考 | 决策 |
|---|---:|---:|---:|---:|---|
| P0 工具链与 canonical 基线 | 10 | 9 | 8 | 72.0 | 立即做 |
| P1 模块边界与运行时闭合 | 10 | 8 | 7 | 56.0 | 立即做 |
| P2 最小垂直切片 | 10 | 8 | 5 | 40.0 | 紧随其后 |
| P4 全量推理规则 | 10 | 6 | 3 | 18.0 | 等 P2/P3 后做 |
| P6 网络、序列化和性能 | 5 | 5 | 2 | 5.0 | 暂不主攻 |

## 八、规格、分支和报告治理

### 规格

- 旧 spec 保留为历史记录，不因为新路线图自动修改状态。
- 新的跨模块实施工作必须通过可用的 LeanSpec `create` 建立新 spec；当前 CLI 不可用时，不手动伪造 frontmatter。
- `in-progress` 只能表示当前主线正在实施且有实际代码/测试进展。
- 每个 spec 的完成条件必须包含编译、测试、集成和文档同步。

### 分支

- `main` 是唯一 canonical 状态。
- 并行分支可以探索，但必须注明基线、验证命令和合并条件。
- Stamp 分支不能直接当作已完成能力；先重放测试、检查调用点，再决定合并或拆分。
- 合并前禁止用 README 勾选代替实际验证。

### 报告

每轮报告固定记录：当前基线、用户指令、事实证据、做出的判断、执行命令、失败原因、未决问题和下一步入口。报告时间不得早于实际变更，不能把历史错误统计写成当前编译结果。

## 九、失衡预警与转向条件

出现以下任一信号，说明路线再次偏离，必须停止扩展范围并重新调查：

- 连续两个变更只增加 TS 文件或注释，没有增加可运行主链覆盖。
- `npm test` 仍只执行单个测试文件。
- 规格状态完成，但测试项未完成或命令无法复现。
- 分支出现多个互相冲突的“已完成”实现，却没有 canonical 合并结果。
- 错误数量下降主要来自删除/注释代码，而不是闭合依赖和行为验证。
- Java 来源路径、模块清单或报告与当前工作树不一致。

## 十、近期执行顺序

下一轮工作只做 P0 的最小闭环：

1. 固定 TypeScript 编译器和 Node 模块策略。
2. 修复测试脚本，使已存在的基础测试都能被统一调用。
3. 修复 `java-master`/`ts-analysis.json` 的来源可复现性。
4. 建立一个 `Nar` 导入 smoke test，先暴露真实的模块边界错误。
5. 以 `Term → TruthValue/Budget → Sentence/Task → Narsese` 作为 P2 的候选垂直切片。
6. 只有 P0 门禁通过后，才重新安排 Stamp、Bag、Memory 和推理规则的具体转写顺序。

本路线的战略原则是：先让系统拥有一条可验证的“生命线”，再让更多模块接入这条生命线；每一次扩展都必须增加可观察能力，而不仅是增加文件数量。
